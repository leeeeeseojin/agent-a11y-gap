# 연구 계획

결과물은 이 레포와 분석 노트북 3개, 2-4쪽 보고서(`report/`)다.
왜 시작했는지는 [origin.md](origin.md)에 있다.

## 연구 질문과 가설

| | 질문 | 가설 |
| --- | --- | --- |
| RQ1 | 브라우저 MCP 스냅샷은 어떤 숨김 패턴에서 표준 접근성 트리와 다른가? | aria-hidden·inert·네이티브 모달처럼 속성으로 숨긴 요소는 스냅샷에 남고, CSS로 렌더를 막은 요소는 사라진다. |
| RQ2 | 그 차이가 에이전트의 성공률, 거짓 성공 보고, 턴 수에 영향을 주는가? | 배경 요소가 노출되면 모달 과제에서 오클릭, 시간 초과, 거짓 성공이 늘어난다. |
| RQ3 | 사람과 에이전트 모두에게 배경을 숨기는 설계는 무엇인가? | 배경을 실제로 렌더하지 않는 설계는 격차를 없애지만, 사람 쪽에서 맥락이 끊기는 비용이 생긴다. |

## 세 층

실험은 세 층으로 나누고, 앞 층에서 차이가 난 조건만 다음 층으로 넘긴다. 모델 비용이 드는 2층을 작게 유지하기 위해서다.

### 1층. 스냅샷 비교

구현 위치: `probe/layer1.ts`, LLM 없음

숨김 패턴 16종을 도구 4종(CDP 전체 접근성 트리, Playwright getByRole, Playwright MCP, Chrome DevTools MCP)으로 읽는다.
노출 여부, 접근성 이름 유지 여부, 클릭용 ref 여부, 그 ref를 눌렀을 때의 결과를 기록한다.

### 2층. 에이전트 과제

구현 위치: `bench/`

과제는 모두 모달을 거쳐야 하는 4개이고, 배경과 시트에 같은 이름의 버튼이 있는 경우를 포함한다.
기본 실험은 과제 4 × 모달 구현 2(B, D) × 모델 3 × 2회로 48회를 Playwright MCP로 돌린다.
처음에는 구현 4 × 3회로 144회를 잡았지만, 모델 사용량 한도에 막혀 줄였다. A·C에서 일어나는 일은
1·3층에서 LLM 없이 이미 정해졌으므로, 배경이 스냅샷에 남는 B와 배경을 내리는 D만 비교한다.
모델은 Gemini 3.8 Flash(Antigravity CLI), GPT-OSS 120B와 Claude Sonnet 5.5(OpenAI 호환 API, OpenRouter)다.
실행기가 모델마다 달라서 턴 수와 성공률은 같은 모델 안에서 B와 D끼리만 비교한다.
본실험에서 문제가 난 GPT-OSS만, 배경 버튼이 걸리는 두 과제의 B·D를 10회씩으로 늘려 추가로 돌린다.
구현 E(B에 열린 동안만 배경 영역 이름을 붙여 `[aria-hidden]` 표시를 살린 것)도 GPT-OSS로 같은 두 과제를 10회씩 돌려,
표시가 배경 클릭을 줄이는지 B와 비교한다.
보조 실험은 Chrome DevTools MCP로 Claude Haiku 5.5(Claude Code 실행기)에게 과제 4 × B·D × 2회를 시킨다.
처음 계획한 3회는 본실험에 맞춰 2회로 줄였다.
채점은 에이전트의 보고가 아니라 서버 상태로 한다. 지표는 확인된 성공, 거짓 성공 보고, 턴 수, 막힌 클릭 수, 대상 중복 수, 시간 초과다.
대상 중복은 `text=저장`처럼 고른 대상이 배경과 시트의 같은 이름 버튼 여러 개로 풀려 거절된 호출이다.
시트 안의 같은 이름 버튼도 함께 세지므로 구현끼리 비교해서 읽는다.

### 3층. 설계 대안

구현 위치: `cases/modal/`, `probe/layer3.ts`, `e2e/`

같은 화면에 모달 구현 네 가지를 적용한다. A는 aria-modal만 있고, B는 배경에 inert·aria-hidden을 걸고,
C는 네이티브 dialog를 쓰고, D는 시트를 여는 동안 배경을 내리고 별도 화면으로 그린다.
사람 기준(배경 숨김, 포커스 가둠, Esc 닫힘과 포커스 복귀)과 에이전트 기준을 한 표로 묶어, 양쪽을 다 만족하는 구현을 설계 권고로 정리한다.

## 미리 정해 둔 것

- inert와 모달 dialog 밖 콘텐츠는 Playwright가 정한 동작이다. 이 문제를 다룬 이슈 [#36938](https://github.com/microsoft/playwright/issues/36938)은
  PR [#43211](https://github.com/microsoft/playwright/pull/43211)로 닫혔다. 그 뒤 1.65 API 리뷰
  [#43792](https://github.com/microsoft/playwright/issues/43792)에서, 로케이터와 ARIA 스냅샷은 이런 요소를 걸러내지 않고
  클릭 같은 동작을 할 때 `element is inert`로 기다리는 쪽으로 정리됐다. 보고서에서는 이 결정을 인용하고 새 발견으로 주장하지 않는다.
  대신 이 설계가 에이전트에게 어떤 실패를 만드는지를 본다.
- aria-hidden 요소가 AI 스냅샷에 남는 것도 정해진 동작이다. PR [#42268](https://github.com/microsoft/playwright/pull/42268)은
  AI 모드 스냅샷이 눈에 보이는 aria-hidden 요소를 일부러 포함한다고 밝히고, 대신 `[aria-hidden]` 표시를 붙였다.
  비공식 정리 문서 두 곳은 스냅샷이 aria-hidden 요소를 뺀다고 적었지만 실제 동작과 다르다. 공식 문서(`Locator.ariaSnapshot`)는
  AI 모드가 기본 모드와 다른 점 네 가지를 적고 있는데, 이 동작은 그 목록에 없고 PR 설명에만 있다.
- 새로 확인한 것은 `[aria-hidden]` 표시의 누락이다. 이 표시는 속성이 직접 붙은 요소에만 달려서, 이름 없는 조상 div에
  속성이 있으면 스냅샷을 줄이는 과정에서 div와 함께 사라진다. 모달 배경을 `#root`에 aria-hidden으로 숨기는 경우가 여기에 해당한다.
  playwright와 playwright-mcp에서 이 누락을 다룬 이슈는 찾지 못했다. 속성 위치만 다른 aria-hidden 패턴 세 개
  (조상 div, 버튼 자체, 이름 있는 영역)를 1층에 넣어 이 차이를 매번 재현하고, CI로 버전이 바뀔 때도 추적한다.
  원인과 고치는 방법은 [aria-hidden-mark.md](aria-hidden-mark.md)에 정리했다.
- 결과는 특정 버전의 값이다. 버전을 결과 폴더 이름에 넣고, CI가 매주 최신 버전으로 다시 돌려 달라진 칸을 남긴다.
- 표본이 작다. 조건당 반복이 적어 모델 순위나 정확한 성공률로 읽지 않는다. 실패 과정의 차이를 중심으로 해석한다.
- 에이전트는 자체 테스트 페이지에서만 돌린다. 사람 참가자가 없는 연구라서 설계 대안 D의 "맥락이 끊기는 비용"은
  여기서 잴 수 없다. 이 비용은 후속 사용자 연구의 질문으로 남긴다.
